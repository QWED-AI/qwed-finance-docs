This page describes how QWED Finance is organised inside.

## Where it runs

QWED Finance is a library. It runs inside your process and makes no network calls. Your code calls a guard with the model's output, and decides what to do with the result: act on it, hold it, or send it to a person.

```mermaid
flowchart LR
    Model["Language model"] -->|"figure, decision,<br/>message or query"| App["Your application"]
    App -->|"calls a guard"| QWED["QWED Finance<br/>(in your process)"]
    QWED -->|"result and, for some calls,<br/>a receipt"| App
    App -->|"verified"| Act["Your bank, payment<br/>or data systems"]
    App -->|"rejected"| Hold["Hold, retry or<br/>human review"]
```

## Verification flow

Every check follows the same path. Input that cannot be parsed, or that is ambiguous, fails closed: it is rejected, never passed through as if it were correct.

```mermaid
flowchart TD
    Call["Your code calls a guard<br/>with the model's output"] --> Parse{"Inputs parse and<br/>are within range?"}
    Parse -->|"no"| Reject["Rejected<br/>(fails closed)"]
    Parse -->|"yes"| Check["Recompute or check<br/>with the guard's engine"]
    Check --> Match{"Matches the model's claim<br/>or the rule?"}
    Match -->|"yes"| Pass["Verified"]
    Match -->|"no"| Fail["Rejected, with the computed<br/>value or the violations"]
```

`CrossGuard`, `UCPIntegration` and the built-in `OpenResponsesIntegration` tools also issue receipts. `UCPIntegration` can return `PENDING_REVIEW` when an amount needs an AML flag.

### Verification receipt

```mermaid

    subgraph Output
        Receipt["Verification<br/>receipt"]

    end

    LLM --> Hash
    LLM --> Guard
    Guard --> Proof
    Hash --> Receipt
    Proof --> Receipt
    Receipt -.-> Sig
    Receipt --> Log
```

Receipts are unsigned until you call `get_signature(key)`. See [Compliance and auditing](/finance/compliance).

### Cross-guard pipeline: SWIFT with sanctions

`CrossGuard.verify_swift_with_sanctions()` runs three steps.

```mermaid
flowchart TD
    Input["SWIFT MT103 message"]

    subgraph "Cross-guard pipeline"
        Step1["1. Message guard<br/>Validate the MT103 format"]
        Step2["2. Extract party names<br/>from the message"]
        Step3["3. Sanctions screening<br/>against the list you pass"]
    end

    Output1["Passed"]
    Output2["Sanctions hit"]
    Output3["Format error"]
    Output4["Unscreened: no sanctions list"]

    Input --> Step1
    Step1 -->|"valid"| Step2
    Step1 -->|"invalid"| Output3
    Step2 --> Step3
    Step3 -->|"clear"| Output1
    Step3 -->|"hit"| Output2
    Step3 -->|"empty or missing list"| Output4
```

An empty or missing sanctions list fails closed as unscreened. A name the screening cannot assess is sent to review, never cleared.

## Deployment

- **Python:** install `qwed-finance` and call the guards from your service.
- **Node.js:** `@qwed-ai/finance` runs the Python package in a child process and passes JSON over stdin; install `qwed-finance` on the same machine. See the [Quickstart](/quickstart).
- **Receipts and audit logs:** `AuditLog` keeps receipts in memory. Export them with `export_json()` and store them where you keep your other audit records, with the signatures stored separately.

## Design principles

### 1. Determinism first

The same input gives the same verdict. No sampling, no confidence scores.

### 2. Exact over approximate

Use solvers and exact arithmetic (Z3, SymPy, mpmath, `Decimal`) instead of floating point or probabilistic scores. Where a numeric method is the only option, as in the IRR fallback, the result says so.

### 3. Audit where it matters

`CrossGuard`, `UCPIntegration` and the built-in `OpenResponsesIntegration` tools generate receipts automatically. Direct guard calls and custom Open Responses tools return result objects; create a receipt with `ReceiptGenerator` when you need an audit record.

### 4. Fail closed

Input that is malformed, ambiguous or missing is rejected, never treated as passing.
